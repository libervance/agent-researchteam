# 내 Windows PC에 만드는 논문·보고서 연구팀 — 0.14.4

소스 ZIP 또는 `Hermes-Research-Setup-0.14.4.zip`의 압축을 모두 푼 뒤 `Start-HermesResearchSetup.cmd`를 실행합니다. 기존 사용자용·관리자용 마법사와 서버 설치 흐름은 유지됩니다. 논문과 보고서를 함께 쓰는 다섯 에이전트(총괄·조사·분석/실험·감사/심사·집필)와 이들을 움직이는 작업 보드·실행기·모델 라우터를 구성하며, 필요한 선택은 마법사에서 끝냅니다. 설정 파일을 직접 작성할 필요가 없습니다. 설치 마지막에 이 PC의 실제 모델·봇으로 다섯 역할이 각각 작은 작업을 끝내야 사용 준비 완료가 됩니다.

## 준비물

- 지원되는 Windows 10/11 x64, Git for Windows, WSL2, Docker Desktop의 Linux 엔진
- Mattermost 관리자용 이메일과 새 비밀번호
- 모델: Anthropic 또는 OpenAI API 키(모델 라우터, 권장), 또는 ChatGPT/Codex 계정(Codex 직접 연결). 비공개 논문을 다루려면 로컬 모델 서버(vLLM·Ollama·LM Studio 등 OpenAI 호환 주소)
- 원고 PDF를 만들려면 TeX(MiKTeX 또는 TeX Live). 없어도 설치는 되지만 집필 작업의 PDF 빌드는 이유와 함께 보류됩니다
- 인터넷 연결

Docker Desktop이 없으면 마법사에서 공식 설치 파일을 다운로드·검증하고 사용자 동의 후 설치할 수 있습니다. Git 자체는 별도로 준비해야 합니다. Mattermost Desktop·NetBird·개별 Hermes Dashboard는 이 로컬 초기 버전에서 필요하지 않습니다.

## 1. 로컬 서버

1. 창을 열면 Docker 준비 상태를 조회합니다. 시스템 전체 설치와 사용자별 설치를 확인하고, CLI·앱·Compose의 공식 서명과 로컬 Linux 엔진을 검사합니다. PATH에서 명령을 못 찾았다는 이유만으로 재설치하지 않습니다.
2. 미설치이고 PC 조건을 충족하면 다운로드·설치 동의 후 `공식 Docker 다운로드·설치`를 누릅니다. 고정된 공식 설치 파일의 SHA-256과 Docker 배포자 서명을 확인한 뒤 설치합니다. 이미 설치된 Docker의 업데이트·제거·재설치는 수행하지 않습니다.
3. Docker Desktop을 열어 약관·초기 설정을 직접 확인합니다. WSL2·가상화·Windows 기능·권한 문제가 있다면 표시되는 안내를 따릅니다. Windows 기능을 자동으로 켜거나 조직 정책을 우회하지 않습니다. 재부팅이 필요하면 직접 재부팅하고 다시 마법사를 실행하세요.
4. `Docker 준비 다시 확인`으로 Linux 엔진과 Compose를 확인합니다. 설치 성공만으로 서버 준비 완료를 표시하지 않습니다.
5. 서버 ID·포트·관리자 이름·이메일·비밀번호를 입력하고 생성 동의 후 `로컬 서버 설치`를 누릅니다.
6. 새 Mattermost·PostgreSQL 컨테이너와 연구용 팀·채널을 만듭니다. 기본 주소는 `http://127.0.0.1:18065`입니다.
7. `내 연구실 열기`에서 만든 관리자 계정으로 로그인합니다. 서버는 이 PC에서만 열리며 외부 공개를 하지 않습니다.

이 마법사가 만든 서버는 같은 ID로 불러오거나 이어서 설치할 수 있습니다. 기존 다른 서버·컨테이너·프로필은 제거하지 않습니다.

### Docker를 사용할 수 없다면

화면에서 PC 조건과 대안을 안내합니다. WSL2가 허용되면 Ubuntu 내부에 Mattermost·PostgreSQL을 직접 설치하는 경로를 별도로 개발할 수 있습니다. WSL2 역시 가상화가 필요합니다. 가상화도 사용할 수 없다면 별도 Linux 서버 또는 기존 Mattermost 서버를 사용하는 구성이 대안이며, 이 경우 같은 Windows PC 한 대에서 서버까지 운영한다는 조건은 변경됩니다. 이 마법사는 아직 이러한 대안의 자동 설치·연결을 제공하지 않습니다. 조직 정책으로 Docker가 금지되면 승인된 환경을 사용하세요.

Docker 설치 파일은 동봉하지 않고 실제 동의·실행 시 다운로드합니다. 현재 고정 버전·공식 URL·체크섬은 `config/docker-desktop.json`에서 확인할 수 있습니다. 설치 파일과 서명 검증이 실패하면 실행하지 않습니다. 고정 파일이 더 이상 제공되지 않으면 임의의 다른 버전을 자동 실행하지 않고 공식 설치 안내를 확인하도록 중단합니다. [Docker 공식 설치·약관](https://docs.docker.com/desktop/setup/install/windows-install/), [공식 릴리스·체크섬](https://docs.docker.com/desktop/release-notes/)

## 2. Hermes·모델

`PC 확인·설치 계획`으로 경로와 고정 릴리스를 검토하고 동의 후 설치합니다. 이미 마법사로 설치한 Hermes가 있다면 `기존 Hermes·인증 확인`을 사용할 수 있습니다. 모델 라우터를 쓸 경우 이 단계의 로그인은 건너뛰어도 됩니다. Codex 직접 연결을 쓸 경우에만 인증 페이지에서 로그인하고 사용할 모델을 선택합니다. 실제 설치 무결성·로그인·모델은 연구팀 연결 전에 다시 확인합니다.

### 기존 Hermes를 그대로 연결하기

1. **이 PC의 기존 Hermes를 선택해 사용합니다**를 선택합니다. 이 선택은 표시된 로컬 설치의 코드를 실행하는 데 대한 명시적 동의입니다. 새 설치의 고정 commit·attestation 검증을 통과했다는 표시로 바꾸지는 않습니다.
2. 데이터 폴더는 기존 `HERMES_HOME`, 코드 폴더는 그 아래 `hermes-agent`인지 확인합니다. 환경 변수의 경로를 기본으로 표시하며 다르면 직접 수정합니다. 현재 지원 범위는 native Windows 소스 설치와 `venv\Scripts\python.exe`입니다. MSIX·WSL 내부 설치를 자동 인수하지 않습니다.
3. **기존 Hermes·인증 확인**을 누릅니다. 공식 저장소 origin, 안전한 로컬 경로·native 실행 파일 형식·소스 commit·런타임 API 호환성을 확인합니다. 인식 단계에서는 `hermes.exe --version`도 실행하지 않으며 화면 버전은 정적 소스 정보 또는 commit입니다. 기존 설치는 다른 commit이나 추가 런처가 있어도 지정 릴리스로 덮어쓰지 않습니다. 경로가 바뀌면 이전 확인 결과를 취소합니다.
4. 인증은 기존 홈에서 읽습니다. 인증 파일 복사·로그인·토큰 갱신·외부 모델 요청을 하지 않으며, 조회 중 파일 쓰기와 네트워크를 차단합니다. Hermes 버전에 따라 인증 함수 인자가 달라도 저장된 인증의 존재 여부를 읽기 전용으로 확인합니다. ‘저장된 인증 발견’은 실제 모델 호출로 계정 유효성까지 검증했다는 뜻이 아닙니다. 기존 모델 선택은 가능한 경우 그대로 표시합니다.
5. 기존 개인 Gateway를 시작·중지·재시작하거나 `--replace`로 교체하지 않습니다. 연구팀은 `research-lead` 프로필의 Gateway와 별도의 팀 서비스만 사용합니다. 기본 Gateway가 모든 프로필을 함께 서비스하도록(`gateway.multiplex_profiles`) 설정되어 있으면 총괄이 두 번 응답할 수 있으므로 설치를 멈추고 안내합니다.
6. 새 연구팀은 `research-*` 프로필 다섯 개를 새로 만듭니다(기존 프로필 복제 없음). 같은 이름의 프로필이 이미 있고 이 마법사의 연구팀 소유가 아니면 아무것도 바꾸지 않고 중단합니다. 이전 4역할 연구팀은 전환 동의로 이어받을 수 있습니다(아래 "이전 4역할 연구팀에서 바꾸기"). 인증은 복제하지 않고 기존 root 인증 경로를 사용하며, 마지막 설치 단계에서 실제 다섯 역할의 작업을 검증합니다.

이 모드에서는 **Hermes 설치**, **모델 계정 로그인**을 실행할 수 없습니다. 기존 인증이 없으면 원래 Hermes에서 계정 상태를 확인하세요. 설치 확인 단계는 읽기 전용이지만, 이후 실제 Hermes 실행 중 정상적인 OAuth 갱신은 원래 Hermes 인증 저장소에서 일어날 수 있습니다. 임의의 기존 프로필을 연구팀 소유로 인수하거나 인증 복제본을 만드는 기능은 없습니다.

기존 사용 모드를 선택하지 않은 새 설치 경로에는 이전과 같은 고정 릴리스·검증 기록 조건을 유지합니다. ZIP을 다른 폴더에 풀어도 기본 홈과 런타임은 공유하므로 격리 설치가 되지 않습니다. 기존 폴더·인증·프로필을 삭제하거나 검증을 끄지 마세요.

### 기존 설치에서 0.14.4 설치기로 갱신

로컬 설치기는 버전 번호가 없는 고정 폴더 `Hermes-Installer` 하나로 관리합니다. 항상 이 폴더의 `Start-HermesResearchSetup.cmd`를 실행하고 창 제목에서 버전을 확인하세요. 설치기 배포 파일을 갱신할 때는 열려 있는 설치기를 닫고 새 패키지의 해시를 검증한 뒤 설치기 파일을 교체합니다. 이전 버전 파일을 섞거나 버전별 폴더를 계속 남기지 않습니다. ZIP과 체크섬은 같은 폴더의 `Packages`에 최신 버전만 보관합니다. 이 폴더는 설치기 배포 전용이며 연구 프로젝트·프로필·토큰을 저장하지 않습니다. 설치기 파일 교체나 실행만으로 Mattermost·Hermes·기존 연구팀은 갱신되지 않습니다. 실제 에이전트 갱신은 사용자가 3단계에서 직접 실행합니다.

1. 1단계에서 **기존 연구 서버 불러오기**, 2단계에서 **기존 Hermes·인증 확인**을 진행합니다. 서버나 Hermes를 재설치하지 않습니다.
2. 3단계는 기존 팀의 토큰·설정을 복원하고, 설치 기록의 구성 지문을 새 설치기의 구성과 비교합니다. 같으면 화면만 확인하고 닫아도 됩니다.
3. 기존 5역할 팀은 자동 감지하며 별도의 갱신 체크박스 없이 **연구팀 업데이트·실제 작업 테스트** 버튼을 표시합니다. 필수 동의 후 이를 누르면 이전 설정·예약 작업을 `RuntimeRoot\research\migrations\고유값`에 백업하고, 팀 서비스·총괄 채팅을 중지한 다음 새 구성을 적용하고 실제 다섯 역할 테스트를 실행합니다. 모델 사용량이 발생하며 작업자 확인은 최대 25분, 총괄 확인은 이후 최대 15분입니다. 대화·세션·논문 작업 폴더와 기존 Mattermost 채널은 유지합니다. 백업 경로와 테스트 결과를 화면에 표시합니다.
4. 베타 교체 항목은 정상적인 5역할 갱신에 선택하지 않습니다. 4역할 분배 서비스를 옮기거나 일반 재설정이 불가능한 오래된 실험 팀을 교체할 때만 사용합니다.

예전 설치기 폴더와 ZIP은 새 설치 확인 후 직접 보관하거나 정리할 수 있습니다. 설치기가 기존 파일을 자동 삭제하지 않습니다. 새 ZIP에도 기존 PC의 인증·토큰·설치 상태가 포함되지 않으며, 이 값은 같은 Windows 사용자와 기존 런타임 폴더에서 복원합니다.

## 3. 다섯 에이전트 — 한 페이지에서 설정

### 팀 구성

| 프로필 (봇 사용자 이름) | 하는 일 | 결과를 쓰는 곳 |
| --- | --- | --- |
| `research-lead` 총괄 | 사용자와 대화, 범위·주장 확정, 작업 보드에 배정, 확인 지점·승인 관리. 원고를 쓰거나 심사하지 않음 | `CLAUDE.md`, `claims.md`(초안 전), `notes/` |
| `research-librarian` 조사 | 문헌 조사·선행 연구, 보고서 초안(실제로 읽은 출처만), 원고 인용 검증 | `notes/`, `reviews/` |
| `research-experimenter` 분석·실험 | 실험 계획(사전 등록) 설계, 승인 후 시간 제한 작업 실행, 결과 수집·판정 | `experiments/`, `evidence/` |
| `research-reviewer` 감사·심사 | 블라인드 심사(신규성·방법·명료성), 의장 종합, 실험 계획 검토, 보고서 감사. 원본 수정 불가 | `reviews/` |
| `research-writer` 집필 | 원고(LaTeX)·주장 목록·빌드·제출 전 점검·반박문. 원고를 수정하는 유일한 역할 | `paper/`, `claims.md`, `outline.md` |

이전 4역할 팀의 관리·조사·분석·감사에 각각 총괄·조사·분석/실험·감사/심사가 대응하고, 논문 원고를 쓰는 집필 역할이 더해졌습니다.

봇 표에서는 표시 이름만 입력합니다. 토큰 입력란과 개별·일괄 발급 버튼은 없습니다. 작업 설정과 필수 동의를 마치고 `연구팀 설치·실제 작업 테스트`(기존 팀은 업데이트·재설정)를 누르면 설정을 먼저 검증한 뒤 누락된 봇 토큰 준비 → 채널 참여 → 연구팀 구성을 백그라운드에서 순서대로 진행합니다. 새 봇 준비에는 연구실 관리자 비밀번호가 필요합니다. 기존 봇과 저장된 토큰은 재사용합니다. 연구팀 설치가 아직 완료되지 않았더라도 서버의 암호화된 봇 인증 파일에서 기존 토큰을 읽어 복원합니다. 이름·작업 설정을 편집해도 인증 복원은 계속됩니다. 기존 팀의 인증 파일이 없거나 소유 정보가 다르면 신규 발급으로 넘어가지 않고 원인을 표시합니다. 실패 시 완료된 토큰은 유지하며, 원인을 해결하고 같은 설치·업데이트 버튼을 다시 누르면 남은 작업을 진행합니다.

새 서버의 기본 채널 주소는 `research-team`입니다. 이미 설치한 서버의 `agents` 등 기존 채널 주소는 자동 변경하지 않으며 계속 사용합니다.

### 모델 연결

- **모델 라우터 (권장):** Anthropic API 키(Claude, 우선)와 OpenAI API 키(장애 시 대체 또는 단독) 중 하나 이상, 그리고 선택으로 로컬 모델 주소·이름을 입력합니다. 이 PC의 `127.0.0.1`에서만 열리는 LiteLLM 라우터(고정 버전 1.105.1)를 전용 Python 환경에 설치합니다. 역할별로 모델 등급(집필·심사·실험: 상위, 조사: 중간, 보조 호출: 경량)을 고르고, 논문의 공개 등급에 따라 경로를 나눕니다.
  - `public`: 클라우드 모델 사용
  - `private`: 로컬 모델 사용. 로컬 모델이 없으면 클라우드로 보내지 않고 작업을 보류하고 이유를 알립니다
  - `air-gapped`: 로컬 모델만, 웹 도구 사용 금지
  API 키는 `RuntimeRoot\research\gateway\env`에만 저장되며 이 폴더는 현재 Windows 사용자와 SYSTEM만 읽을 수 있습니다. 에이전트는 작업마다 실행기가 만든 일회용 라우터 키만 받습니다.
- **Codex 직접 연결:** 2단계에서 로그인한 ChatGPT/Codex 모델을 다섯 역할이 함께 씁니다. 라우터가 없으므로 공개(`public`) 논문·보고서만 처리하고, 비공개 논문은 보류합니다.

### 작업 설정

- **작업 폴더:** 기본 제안은 문서 폴더의 `Hermes Research Workspace`입니다. 논문마다 폴더가 생기고, `_template`(논문 템플릿), `reports`(보고서 보드), `.scratch`가 함께 만들어집니다. 설치·인증·운영 폴더는 작업 폴더로 쓸 수 없습니다.
- **저장 위치 안내:** 설치 결과 화면에 `RESEARCH_PATHS.md`의 전체 경로가 나옵니다. 이 파일은 작업 폴더, 논문별 폴더와 Git 원격, 보드·기록, 실행기 복제본, 로그, 프로필, Mattermost 서버 배포 위치를 한 곳에 표시합니다. 새 논문 보드를 만들 때 갱신됩니다. 총괄에게 `파일은 어디에 저장돼?`라고 물어도 현재 위치를 확인할 수 있습니다.
- **요청할 사람 계정:** Mattermost 실제 사용자 이름. 설치 중 활성 사람 계정·채널 참여 여부를 확인하고, 총괄은 이 계정의 요청에만 응답합니다. 다른 봇의 글로는 작업이 시작되지 않습니다.
- **작업 시간 한도:** 작업 하나(예: 원고 수정 한 번, 심사 한 건)의 최대 실행 시간입니다. 기본 180분, 30~720분. 넘으면 작성한 파일과 중간 기록을 `partial`로 저장하고 스레드에 알립니다.
- **논문 심사 병렬 처리 수:** `research-reviewer` 봇·프로필은 하나입니다. 사용자가 논문 심사 라운드를 요청하면 총괄은 새로움·방법·명료성 심사 작업을 각각 하나씩 작업 보드에 만듭니다. 실행기 수를 1로 두면 세 작업을 순차 처리하고, 2면 최대 두 건, 3이면 세 건을 동시에 처리합니다. 봇이나 사람 수가 아닙니다. 일반 대화에서 심사 작업이 없다면 심사 모델은 호출되지 않습니다. 기본 3이며 PC 자원에 맞춰 1~3을 선택할 수 있습니다.
- **체크리스트 순서:** 필수 항목 전체 동의 → [필수] 모델 전송 → [필수] 공개 웹 검색 → [필수] 설치·실제 테스트 → 기존 팀 감지 결과. 정상 5역할 갱신에는 별도 선택이 없습니다.
- **필수 동의:** 모델 전송·공개 웹 검색·실제 설치 테스트의 세 항목만 전체 동의에 포함됩니다. 처음에는 선택되지 않습니다.
- **이전 4역할 베타 팀:** 해당 팀이 실제로 감지될 때만 이전 동의가 나타납니다. 정상 5역할 팀에는 표시되지 않습니다. 오래된 5역할 팀도 일반 갱신으로 처리하고 구성이 달라졌다면 이전 설정과 예약 작업을 자동 백업합니다.
- **중단된 설치 계속:** 프로필 구성 후 보고서 보드 초기화에 실패했던 0.14.2 설치는 다섯 프로필의 같은 팀 표식과 설치 위치, 총괄의 서버·채널·인증을 검증하여 같은 프로필로 이어갑니다. 0.14.3부터는 프로필 생성 전에 팀 소유 기록과 봇 인증을 먼저 저장하므로 실패 후 재시도에서도 같은 팀을 인식합니다. 프로필을 수동 삭제하지 마세요.
- **보드 초기화 오류:** 기존 Hermes의 제한된 자식 프로세스 실행 경로에 확인된 Git 실행 위치를 추가하고 프로필 변경 전에 실행을 확인합니다. 초기화 실패 시 `ResearchReportsBoardinitFailed`와 함께 비밀값을 가린 원인을 표시합니다.

### 설치 중 실제 작업 테스트

`연구팀 설치·실제 작업 테스트`를 누르면 프로필 다섯 개와 서비스를 구성한 뒤, 작업 폴더에 `_selftest-날짜` 폴더를 만들고 연구 채널의 스레드에서 다음을 실제로 실행합니다.

1. 조사: arXiv에서 실제 논문 1편을 찾아 ID와 함께 기록
2. 감사·심사: 그 논문의 arXiv 페이지를 열어 제목·연도를 블라인드로 대조
3. 집필: LaTeX 문장 한 줄 작성
4. 분석·실험: 터미널에서 명령 실행 결과를 기록
5. 총괄: 자기 프로필·스킬로 작업 보드를 읽고 답변

모두 끝나면 작업 기록(해시 체인)을 검증하고 결과 파일을 스레드에 올린 뒤 다시 내려받아 SHA-256을 비교합니다. 하나라도 실패하면 **사용 준비 미완료**로 표시하고 이유를 보여 줍니다. 모델 사용량이 발생하며 작업자 확인은 최대 25분, 총괄 확인은 이후 최대 15분입니다. 결과는 `RuntimeRoot\research\live-test.json`과 테스트 폴더의 `.tasks/ledger.jsonl`에 남습니다.

## 4. 사용하기

사용 준비 완료 후 연구 채널에서 총괄 봇(`@research-lead`)을 멘션합니다. 진행 상황은 각 담당 봇이 같은 스레드에 올리고, 사용자의 확인이 필요하면 멘션으로 알립니다.

| 요청 예 | 진행 |
| --- | --- |
| `@research-lead 재생에너지 저장 기술에 대한 보고서 작성해줘` | 총괄이 요청·질문·범위를 정리 → 조사 담당이 실제로 읽은 출처로 초안·출처 목록 작성 → 감사 담당이 문장마다 출처와 대조(블라인드) → 지적이 있으면 조사 담당이 수정하고 새 버전을 다시 감사(최대 3회) → 통과한 보고서를 Word 파일로 첨부 |
| `@research-lead 장기 기억 에이전트 주제로 논문을 시작하자` | 대상 학회·핵심 기여 한 문장·가장 가까운 선행 연구 확인(대화) → 주장과 실험 계획 → 개요(사용자 승인) → 절 단위 집필 |
| `@research-lead 심사 라운드 돌려줘` | 집필 담당이 PDF 빌드 → 세 심사(신규성·방법·명료성)와 인용 검증이 동시에 블라인드로 진행 → 의장 종합(수정 계획·판정) → 사용자에게 확인 요청. 어떤 지적을 받아들일지는 사용자가 결정 |
| `@research-lead 이 주장을 확인할 실험을 설계해줘` | 실험 담당이 사전 등록 계획 작성 → 심사 담당이 계획 검토 → 사용자가 승인해야 실행 → 시간 제한 작업 → 미리 정한 기준으로 판정. 승인된 계획은 수정할 수 없고 변경은 별도 승인 |
| `@research-lead 어디까지 됐어?` | 작업 보드 상태를 몇 줄로 답변 |

공개 등급은 논문 폴더의 `CLAUDE.md`에 있는 `**Sensitivity:**` 줄로 정합니다. 기본은 `public`이며, 논문을 시작할 때 총괄이 묻습니다. 보고서는 공용 `reports` 폴더(공개)에 쌓이고, 비공개 주제는 별도 폴더로 만듭니다.

결과는 모두 작업 폴더의 git 저장소에 남습니다. 각 작업이 어느 버전(commit)을 읽고 무엇을 만들었는지는 `.tasks/ledger.jsonl`에서 확인할 수 있으며, 심사·감사 결과는 그 버전에 대해서만 유효합니다.

논문마다 별도 Git 저장소가 만들어지지만, 기본 원격은 **이 PC의** `RuntimeRoot\research\boards\<논문>.git`입니다. 총괄은 `research_board.py project-create <이름>`으로 폴더·보드·채널 연결·등록을 한 번에 준비합니다. GitHub 저장소를 자동 생성하거나 업로드하지 않습니다. 여러 PC에서 같은 논문을 작업하려면 `--remote <공유 Git URL>`로 모든 실행기가 접근할 수 있는 원격을 지정하고 다른 PC의 `RuntimeRoot\research\papers`에도 등록해야 합니다. 비공개 원고와 데이터의 공개 범위도 원격 설정에서 직접 확인하세요.

총괄만 Mattermost 채팅 요청을 받습니다. 다른 네 봇은 작업 보드의 실행기가 진행 상황을 올릴 때 사용하며 채팅 요청은 받지 않습니다. 실행기는 작업마다 한 개의 진행 글을 갱신합니다. 내부 총괄 조정기가 작업 보드의 완료·중간 결과를 읽고 다음에 허용된 작업을 계획하므로 봇끼리 Mattermost에서 호출하지 않습니다. 논문의 기여·개요·심사 판정과 실험 계획 승인은 여전히 사용자가 결정합니다. Hermes 작업당 도구 호출 한도는 80회이며, 한도에 걸리면 `.tasks/attempts/`에 중간 기록을 남깁니다. 안전한 읽기·쓰기 작업은 한 번 이어서 시도하지만 실험 실행은 승인된 재시도 규칙을 먼저 확인합니다. 백그라운드 총괄도 한도에 걸리면 `research/run/lead-attempts/`에 결과를 남기고 사용자에게 대화로 재개해 달라고 알립니다.

## 5. 안전 장치

- **블라인드 심사:** 심사·감사·인용 검증 담당은 git 기록과 작업 보드가 없는 사본에서 실행되며, 기억(memory)과 이전 세션 검색이 꺼져 있습니다. 총괄은 심사 요청에 저자의 의도나 이전 라운드의 변경 사항을 넣지 않습니다.
- **역할별 출력 경로:** 실행기는 각 역할이 쓸 수 있는 경로(위 표)의 변경만 커밋하고 나머지는 버립니다. 심사 담당이 원고를 고쳐도 반영되지 않습니다.
- **승인 고정:** 실험 계획은 승인 기록이 생기면 수정할 수 없고, 수정하면 되돌린 뒤 작업을 실패로 표시합니다.
- **지침 무결성:** 설치 파일은 `team/manifest.json`, 설치된 각 프로필의 지침·스킬은 `profile-manifest.json`과 SHA-256으로 대조합니다. 지침이 바뀐 프로필의 작업은 실행하지 않고 재설치를 안내합니다.
- **추가 전용 기록:** 작업 기록의 각 줄은 앞 줄의 해시를 담습니다. 기록이 고쳐지면 다음 작업 때 스레드로 알리고, 끊긴 지점을 기록에 남깁니다.
- **비밀값 분리:** 봇 토큰과 라우터 비밀값은 실행기만 가지며 에이전트 프로세스에는 전달되지 않습니다. 총괄 봇 토큰만 총괄 프로필의 `.env`에 있습니다. 공급자 API 키는 라우터 폴더에만 있습니다.
- **재시도·시간 한도:** 일시적인 모델 오류(요청 한도·과부하·시간 초과·5xx)는 30초·2분 뒤 다시 시도하고, 작업 시간 한도를 넘으면 중단합니다.
- **결과 전달 확인:** 첨부한 파일은 다시 내려받아 SHA-256을 비교합니다. 전달 실패는 스레드에 알리며 원고 수정 사유로 돌리지 않습니다.

같은 Windows 사용자나 관리자의 악의적인 파일 수정까지 막는 OS 샌드박스는 아닙니다. 에이전트는 Git Bash 터미널에서 명령을 실행할 수 있으므로, 연구팀은 신뢰하는 개인 PC에서 사용하세요.

## 6. 베타 실험에서 기존 팀 교체하기

베타 이전 동의는 0.12.x의 4역할 연구팀(분배 서비스)을 감지했을 때만 표시됩니다. 정상적인 5역할 팀은 자동 감지하여 같은 프로필·봇으로 갱신합니다. 오래된 5역할 구성도 별도 교체 옵션 없이 일반 갱신하며, 구성 파일이 다르면 자동 백업합니다.

1. 분배 서비스에 작업 종료를 요청하고, 실행 중인 요청이 없음을 확인합니다. 작업 중이면 강제 종료하지 않고 중단합니다.
2. 이전 설정·예약 작업을 `RuntimeRoot\research\migrations\고유값`에 백업합니다. 대화·세션·산출물·SQLite 기록은 원래 위치에 그대로 둡니다.
3. 분배 서비스 예약 작업을 비활성화합니다(삭제하지 않음).
4. `research-lead`·`research-reviewer` 프로필은 새 팀이 이어받습니다(지침·스킬·설정 교체, 기록·세션 유지, 총괄의 Mattermost 연결 다시 사용). `research-scout`·`research-worker`는 그대로 둡니다.

오래된 5역할 팀은 현재 팀의 설정·예약 작업을 먼저 백업하고 서비스를 중지한 뒤 같은 다섯 프로필을 새 구성으로 갱신합니다. 기존 채널, 봇 토큰, 세션과 작업 보드 기록은 유지합니다.

## 7. 실행과 재시작

Windows 로그인 시 두 예약 작업이 자동 실행됩니다. 

- `Hermes Research … - team service`: 모델 라우터와 실행기(조사·실험·집필 1개씩, 심사 1~3개). 멈춘 실행기는 자동으로 다시 시작합니다. 상태는 `RuntimeRoot\research\service-status.json`, 로그는 `RuntimeRoot\research\logs`.
- `Hermes Research … - lead chat`: 총괄의 Mattermost Gateway.

`RuntimeRoot\research\private`(봇 토큰)·`gateway\env`(API 키), 작업 폴더의 비공개 논문, 로그를 Git·진단 ZIP·공개 이슈에 올리지 마세요.

### 0.14.4: 설치 테스트가 메시지를 남긴 뒤 멈춘 경우

- Mattermost 진행 글과 보드 저장 완료는 다릅니다. 네 작업자 결과 저장 후 총괄 확인, 기록 무결성 검사, 첨부 전달 검증까지 통과해야 설치가 완료됩니다. 설치 로그에 역할별 상태와 현재 검증 단계를 표시합니다.
- 0.14.3까지는 여러 작업자가 완료 기록(`.tasks/ledger.jsonl`)을 동시에 추가하면 Git 재배치 충돌로 보드가 `running`에 남을 수 있었습니다. 0.14.4는 이미 저장된 기록을 보존하며 새 항목을 순서대로 연결해 재시도합니다.
- 실제 산출물 충돌은 덮어쓰지 않습니다. 실행기 복제본의 완료 커밋을 `refs/research/pending-publication`에 보존하며 다음 확인 전에 저장을 재시도합니다. 수동 해결이 필요한 충돌·중단된 재배치는 오류로 표시합니다. 설치 테스트는 해당 보드 실행기 오류를 읽어 전체 시간 초과까지 기다리지 않고 원인을 표시합니다.
- 기존 버전에서 이미 버려진 미전송 완료 커밋은 자동 복구하지 않습니다. 필요하면 Git reflog로 복구해야 합니다. 일반 설치 재시도는 기존 봇·프로필을 갱신하고 새 테스트 폴더를 만듭니다. 기존 테스트 폴더와 대화는 보존됩니다.
- 기존 서버의 채널 ID와 채널 이름은 갱신 시 유지합니다. `research-team`은 새 설정의 기본값이며, 기존 `agents` 채널을 자동으로 이름 변경하지 않습니다.
